# Поставка Memo на Timeweb

## 1. Назначение и окружение

Адрес — [cj999935.tw1.ru/mind-assistant/](https://cj999935.tw1.ru/mind-assistant/). Единственный реестр назначения — [deploy/timeweb.json](deploy/timeweb.json). Каталог публикации — `/home/c/cj999935/public_html/mind-assistant`. Корневой Purpur и `stonehaus/` не входят в поставку. `infra/timeweb/targets.json` и `npm run timeweb` обслуживают только статические приложения.

Проверены веб-PHP 8.2.36, CLI PHP 8.4.28 и Python 3.10.12. Нужны PDO MySQL, curl, DOM, fileinfo, `mysqldump` и HTTPS-доступ к GitHub. Версия веб-PHP относится ко всему сайту и ради приложения не меняется. Локально используются PHP 8.4/MySQL 8.4 в Docker. CI проверяет API и собранный артефакт на PHP 8.2 и 8.4. Node и Docker на хостинге не нужны.

## 2. Первичная настройка сервера

В панели создаётся отдельная MySQL-база и пользователь `cj999935_mindassistant`. В приватном `/home/c/cj999935/.sandbox/mind-assistant/config.php` хранится PHP-массив по образцу `backend/config.example.php`: `DB_HOST=localhost`, `DB_PORT=3306`, имя и пользователь этой базы, её пароль, `APP_ENV=production`. Все значения — строки. Права файла — `600`, приватных каталогов — `700`. Пароль не передаётся в GitHub, Git, аргументах команд или журнале.

Через проверенный SSH alias `timeweb-sandbox` установите `deploy/receiver.py` и `deploy/pull.py` в этот приватный каталог. Скопируйте `deploy/timeweb.json` туда под именем `target.json`. Перед заменой рабочих скриптов проверьте текущие файлы, загрузите новые под временными именами, выполните `python3 -m py_compile` и переименуйте. После изменения worker-кода повторите установку: артефакт приложения не обновляет служебные скрипты.

В панели Crontab создаётся одно задание каждые две минуты (`*/2 * * * *`):

```text
/usr/bin/python3 /home/c/cj999935/.sandbox/mind-assistant/pull.py >> /home/c/cj999935/.sandbox/mind-assistant/deploy.log 2>&1
```

Оно забирает только артефакт Memo из публичного Sandbox. Постоянный SSH-ключ аккаунта в Actions не используется. На этом аккаунте проверка показала, что `command=` в `authorized_keys` не ограничивает запускаемую команду. Такой ключ нельзя считать изолированным ключом деплоя.

## 3. Выпуск из Sandbox

1. Опубликуйте исходный коммит в `main` и дождитесь успешного **Harness** именно для его SHA: общие проверки, сборки и API на PHP 8.2/8.4.
2. Из чистой рабочей папки с этим коммитом выполните:

   ```bash
   npm run release:memo
   ```

   Команда проверит актуальность `origin/main` и CI, затем передвинет `release/mind-assistant` на этот SHA. Запустится **Deploy Memo**. Альтернатива — ручной запуск workflow на `main` в Actions. Обычный push в `main` приложение не публикует.

3. Дождитесь успешного завершения **Deploy Memo**. Workflow повторно сверяет main/CI, собирает детерминированный архив и публикует его вместе с `deployment.json` в служебную ветку `deploy/mind-assistant`. Используется только временный встроенный `GITHUB_TOKEN`. SSH- и MySQL-секретов в GitHub нет.
4. Задание Timeweb проверяет SHA, последнюю проверку Harness и контрольную сумму. Workflow ожидает до восьми минут публичную метку `release.json` с теми же SHA, суммой и `deploymentStatus=ready`.

Ветки `release/mind-assistant` и `deploy/mind-assistant` служебные. Исходный код меняется через `main`. Архивы сохраняются с именами, включающими SHA. Если этот SHA уже запрашивался, команда не создаёт повторный push: проверьте Actions и приватный `deploy.log`, после устранения причины повторите существующий workflow.

Для диагностики с локального компьютера предусмотрен `npm run deploy:memo -- plan`. Он собирает чистый текущий коммит, передаёт архив приватно, проверяет состав и синтаксис PHP, но не меняет БД и публичные файлы. Прямой `publish --apply` — запасной путь через существующий SSH alias с теми же проверками main/CI и серверным receiver. Обычный выпуск выполняется через Actions.

## 4. Серверная поставка

Receiver блокирует параллельную поставку, проверяет архив и распаковывает только разрешённые файлы в приватный временный каталог. Symlink, выход из каталога, `.env`, локальная конфигурация и посторонние файлы запрещены. PHP проходит проверку синтаксиса. Публичным каталогам явно задаются права `755`, файлам — `644`: Cron может работать с `umask 077`. Конфигурация получает отдельные права `600`.

До миграции создаётся SQL-копия **только** базы Memo в приватном `backups/`, включая медиа. Реквизиты `mysqldump` получает через временный файл `600`, который удаляется после команды. Ошибка или таймаут backup останавливает публикацию. Затем применяется идемпотентная схема, создающая отсутствующие таблицы. Изменения существующей схемы требуют отдельных совместимых миграций. Старый PostgreSQL-дамп автоматически не импортируется.

После распаковки receiver добавляет рабочую копию приватного конфига как `config.local.php` с правами `600`. Она защищена HTTP 403 через `.htaccess` и отсутствует в архиве GitHub. Это необходимо на данном хостинге: веб-PHP не читает файлы вне `public_html`, даже когда `is_readable` возвращает `true`. Перед первой поставкой запрет HTTP-доступа и чтение конфигурации самим PHP проверены на синтетическом файле без секретов. Приватный `config.php` остаётся источником для следующих поставок. Прежний публичный каталог переносится в приватный `releases/`, новый занимает его место. Здесь используются два переименования с коротким промежутком недоступности. Symlink-публикация на этом аккаунте дала HTTP 500 и не применяется.

Receiver проверяет по HTTPS метку релиза, API/БД, страницу, вложенный маршрут и HTTP 403 для приватных путей. После успеха метка меняется с `verifying` на `ready`. Повтор установленного SHA с той же суммой выполняет проверку без повторной миграции/backup. Другая сумма для того же установленного SHA отклоняется.

## 5. Проверка и восстановление

После выпуска проверьте регистрацию, вход, создание и сохранение проекта, карточки и файла, выход и повторный вход отдельным тестовым пользователем. Проверьте соседние сайты. Удаляйте только созданные проверкой данные.

Проверяйте `release.json` со свежим параметром `check=<текущее время>`: запрос с постоянным SHA может получить закэшированную метку предыдущего релиза, если начался до обновления. Actions проверяет HTTPS через curl по IPv4 с обычной проверкой TLS и выводит причину ожидания или сетевой ошибки.

HTML (включая вложенные SPA-маршруты) и `release.json` получают `Cache-Control: no-cache, max-age=0, must-revalidate` через Apache `mod_headers`. Браузер перепроверяет сохранённый HTML перед повторным использованием. Имена JS/CSS содержат хеш сборки. Браузеру, уже сохранившему HTML старого выпуска без этого заголовка, может понадобиться одно обычное обновление страницы.

При неуспешной HTTPS-проверке receiver возвращает прежние файлы, сохраняет неудачный релиз и SQL-копию. **Изменения БД автоматически не откатываются.** Файловый rollback покрыт изолированными тестами. Реальная SQL-копия после переноса старых данных восстановлена отдельно в Docker с PHP 8.2/MySQL 8.4, сверкой всех таблиц и API. Команда и границы проверки — в [проверке восстановления](recovery.md). Восстановление живой production-БД не выполнялось.

Резервные копии: `~/.sandbox/mind-assistant/backups/*.sql`, рядом JSON с исходным и прежним релизом. Прежние файлы: `~/.sandbox/mind-assistant/releases/previous-*`. Текущий релиз: публичный `release.json`. Диагностика: приватный `deploy.log`. Автоматического удаления backup и старых архивов нет: следите за квотой и очищайте их отдельной осознанной операцией.

При неизвестном результате сначала сопоставьте Actions, публичную метку, текущий каталог и backup. Не повторяйте миграцию и не восстанавливайте SQL вслепую. Для совместимого файлового отката остановите pull в панели и выберите подтверждённый предыдущий каталог. Для несовместимой схемы нужны согласованная пара файлов/БД и отдельное разрешение на восстановление данных. Процедура — [восстановление Timeweb](../../.agents/skills/timeweb/references/recovery.md).
