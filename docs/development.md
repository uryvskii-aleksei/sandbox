# Разработка

## 1. Приложения

Репозиторий объединяет приложения, которым могут требоваться разные языки и среды выполнения. Общими остаются правила качества, GitHub и описание публикации. Изменение одного приложения не должно требовать изменения всех остальных.

Начинайте с папки приложения и его README. Документируйте реальные команды, необходимые переменные окружения без значений секретов, публичные маршруты и требования хостинга. Для размещения в каталоге домена настройте base URL, адреса ресурсов, маршрутизацию и callback URL. Для поддомена подтвердите отдельную привязку в панели Timeweb.

## 2. Рабочий цикл

Прочитайте задачу и принятые решения, проверьте рабочую папку и незавершённые изменения. Для новой задачи используйте актуальную `main` и отдельную ветку. Изолированный worktree нужен при занятой основной папке или по поручению.

Существенные вопросы выясняйте до зависимой реализации. Исследование заканчивается выводом и следующим шагом, если реализация не была поручена. Для реализации выполните нужные изменения, проверьте поведение и контракты. При поручении подготовить PR опубликуйте ветку и PR, затем проверьте CI для его текущего коммита.

Роли planner, coder, reviewer, qa и designer помогают распределять работу, когда делегирование разрешено. QA проверяет поведение по требованиям, reviewer анализирует код и дизайн, designer описывает интерфейс и его состояния. Небольшую связную задачу агент может выполнить сам. Автор не называет собственную проверку независимым ревью.

## 3. Проверки

Для обвязки используется `npm run check`. Для приложения запускаются его собственные проверки: типы и линтер, нужные тесты, сборка и браузерные сценарии в зависимости от изменения. Добавляйте соответствующие задания в CI при создании приложения.

Тесты проверяют наблюдаемое поведение, обработку ошибок и важные границы. Простые исправления текста не требуют тестов, повторяющих этот текст. Успешная сборка не доказывает работоспособность интерфейса. После изменений общего пакета проверяйте его затронутых потребителей.

## 4. Документация и поставка

Описание PR содержит цель, изменения, фактические проверки и при необходимости план. Исследования и технические решения связываются с issue и документацией без копирования одного текста в несколько мест. Коммиты и описания пишутся по-русски.

Публикация — отдельный результат. Перед ней известны конкретный артефакт, адрес, папка на сервере и способ восстановления. На хостинг отправляется содержимое сборки выбранного приложения. Исходный монорепозиторий, ключи, зависимости разработки и серверные секреты не должны попадать в публичную папку сайта.
