# Перенос старых данных Memo

## 1. Результат и соответствие схем

Исторический PostgreSQL-дамп перенесён в отдельную MySQL-базу Memo с явным владельцем. Исходный проект был пустым. Пять записей ссылались на отсутствующие проекты `0` и `1`. Политика `recover` создала по одному восстановленному проекту для каждого отсутствующего ID. Итог — 3 проекта, 5 карточек, 2 группы и 2 текстовых поля. Исходные родительские связи и содержимое сохранены. Числовые UTF-8-байты старых текстовых полей декодированы. Пустые координаты становятся `(0, 0)`, старые sentinel parent `0`/`-1` — `NULL`.

Поле старого проекта `pages` было счётчиком без отдельной таблицы страниц. Новая версия считает карточки по фактическим данным. Новые аккаунты и их данные не заменяются. Журнал `legacy_imports` связывает SHA исходного дампа, нормализованный payload, владельца и созданные ID. Повтор возвращает `already-imported`, сохраняя пользовательские правки.

## 2. Подготовка приватного payload

Дамп, JSON, конфигурация и отчёты остаются вне Git. Каталоги имеют права `700`, файлы — `600`. Нужен Docker Desktop.

```bash
node apps/memo/scripts/prepare-legacy.mjs \
  --dump .imports/private/mind-assistant/legacy-historical-postgresql.dump \
  --output .imports/private/mind-assistant/legacy-migration.json
```

Команда читает один снимок дампа, поднимает одноразовый PostgreSQL без сети и опубликованных портов, выгружает проекты/записи, затем удаляет только свой контейнер и временные файлы. Существующий output не заменяется. Содержимое записей в stdout не выводится.

## 3. План и применение

До применения владелец регистрирует аккаунт в новом приложении. Его email передаётся только в приватной команде, не в публичных документах. Импортёр размещается рядом с приватным конфигом хостинга, вне `public_html`. В артефакт приложения он не входит.

```bash
php /private/path/import-legacy.php plan \
  --input /private/path/legacy-migration.json \
  --app-root /home/c/cj999935/public_html/mind-assistant \
  --config /home/c/cj999935/.sandbox/mind-assistant/config.php \
  --owner-email OWNER_EMAIL --orphan-policy recover
```

`plan` только читает БД, проверяет владельца, схему данных, ссылки, циклы и журнал. Без явного `recover` orphan-карточки блокируют применение. Сверьте SHA, владельца, количество и правила преобразования до записи.

Для применения удерживайте тот же файловый lock, что использует receiver поставки, и создайте штатную SQL-копию только базы Memo через приватный конфиг. После этого выполните ту же команду с `apply` вместо `plan`. Импортёр дополнительно использует MySQL `GET_LOCK`. Таблица журнала создаётся до транзакции, а новые проекты, карточки, поля и запись журнала — одной транзакцией. Перед commit сверяется содержимое. Ошибка откатывает записи этой попытки. После commit создайте вторую копию и повторите `plan` для подтверждения `already-imported`.

Уже выполненный перенос не нужно повторять после выпуска приложения. Отмена переноса и восстановление живой БД требуют отдельного выбора согласованной копии с учётом последующих правок.

## 4. Проверки

```bash
npm run test:legacy:memo
MEMO_TEST_PHP_VERSION=8.2 npm run test:legacy:memo
```

Синтетическая проверка создаёт отдельную MySQL-базу и проверяет UTF-8, значения/порядок полей, координаты, родителей, сохранение посторонних данных, повтор после пользовательской правки, отказ при другом владельце/payload, циклах и межпроектных связях, rollback при ошибке SQL. В CI обе версии PHP проверяются отдельно.

Приватный реальный payload дополнительно проверяется через `node apps/memo/scripts/test-legacy.mjs --payload PRIVATE_JSON`. В stdout попадают только агрегаты. SQL-копия после реального импорта прошла [восстановление и проверку API](recovery.md).
