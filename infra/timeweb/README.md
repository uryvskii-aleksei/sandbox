# Timeweb: виртуальный хостинг

## 1. Подключение

Используем обычный виртуальный хостинг Timeweb через SSH/SFTP. Cloud API и MCP Timeweb Cloud к этому виду хостинга не относятся.

Технический домен — [cj999935.tw1.ru](https://cj999935.tw1.ru/). Сервер — `vh460.timeweb.ru`, основной пользователь — `cj999935`, каталог сайта — `/home/c/cj999935/public_html`. На этом компьютере настроен alias `timeweb-sandbox` с отдельным ключом `~/.ssh/sandbox_timeweb_ed25519`. Проверены вход по ключу, SFTP и передача через rsync со сверкой SHA-256 вне публичного сайта.

[connection.json](connection.json) содержит несекретные настройки аккаунта для команды `npm run timeweb -- check`. Эта проверка работает и до появления первого приложения, ничего не загружая в корень сайта.

Включите SSH в панели и возьмите имя сервера и логин из реквизитов доступа. [Официальная инструкция SSH](https://timeweb.com/ru/docs/virtualnyj-hosting/podklyuchenie-k-serveru-hostinga/podklyuchenie-po-ssh/), [SFTP](https://timeweb.com/ru/docs/virtualnyj-hosting/podklyuchenie-k-serveru-hostinga/podklyuchenie-po-sftp/).

Создайте отдельный SSH-ключ и установите открытый ключ для нужного аккаунта хостинга. Закрытый ключ храните локально. Используйте [пример SSH-конфигурации](ssh-config.example), заменив реквизиты реальными. Сверьте fingerprint сервера через доверенный канал перед добавлением в `known_hosts`. `ssh-keyscan` сам по себе подлинность сервера не подтверждает. Проверка ключа сервера остаётся включённой.

```bash
ssh -o BatchMode=yes -o StrictHostKeyChecking=yes timeweb-sandbox pwd
```

Это проверяет доступ без публикации. Команды обвязки используют уже настроенный SSH alias и не запрашивают пароль. Закрытые ключи и `known_hosts` не копируются в репозиторий.

На виртуальном хостинге чтение `/etc/ssh/ssh_host_ed25519_key.pub` может быть запрещено. Такая ошибка не означает, что пользовательский ключ не установился. В этом аккаунте сервер подтверждён чтением по SSH одноразовой приватной метки, созданной через авторизованную веб-консоль Timeweb. После сверки его ключ сохранён в `known_hosts`, строгая проверка осталась включённой. Для нового компьютера ключ сервера нужно подтвердить заново через доверенный канал.

## 2. Цели приложений

[targets.json](targets.json) — реестр назначений статического помощника. В нём зарегистрированы `stonehaus-v1`, `stonehaus-v2` и `stonehaus-v3`, каждый со своим каталогом сборки и HTTPS-адресом. PHP-приложение Memo использует собственный [реестр назначения](../../apps/memo/deploy/timeweb.json) и [процедуру поставки](../../apps/memo/deployment.md). Для новых статических публикаций нужно зарегистрировать конкретные каталоги. Добавляйте цель после создания приложения и подтверждения каталога в панели Timeweb. Для текущего технического домена адрес приложения будет иметь вид `https://cj999935.tw1.ru/<имя>/`.

Пример структуры, который нужно заполнить фактическими значениями:

```json
{
  "version": 1,
  "provider": "timeweb-shared",
  "targets": {
    "example-app": {
      "app": "apps/example-app",
      "buildDir": "dist",
      "sshHost": "timeweb-sandbox",
      "remotePath": "public_html/example-app",
      "url": "https://cj999935.tw1.ru/example-app/"
    }
  }
}
```

| Поле         | Значение                                                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Имя цели     | Уникальное имя в kebab-case, например приложение и окружение                                                                                                  |
| `app`        | Папка приложения непосредственно внутри `apps/`                                                                                                               |
| `buildDir`   | Отдельный каталог статической сборки внутри приложения, без `..` и symlink                                                                                    |
| `sshHost`    | Имя из личного `~/.ssh/config`, не пароль и не произвольная SSH-команда                                                                                       |
| `remotePath` | Существующий каталог сайта: путь относительно домашнего каталога SSH либо абсолютный путь. Должен содержать компонент `public_html`, без `~`, пробелов и `..` |
| `url`        | Полный HTTPS-адрес приложения, включая префикс каталога, если он есть                                                                                         |

На одном SSH alias каталоги разных целей не должны пересекаться. Используйте одно имя alias для одного аккаунта и одинаковый вид путей. Разные aliases и серверные symlink могут указывать в одну папку — такую ситуацию необходимо проверить перед настройкой целей.

Для поддомена создайте отдельный сайт/привязку в панели. Для каталога основного домена используйте выделенную папку внутри его `public_html` и настройте base URL приложения. Существующие сайты, DNS, загрузки и серверные файлы не меняются автоматически.

## 3. Проверка и публикация

Для импортированных сайтов предусмотрена поставка проверенного текущего `main` по личному SSH с резервными копиями и файловым возвратом при ошибке HTTPS:

```bash
npm run deploy:sites -- plan purpur
npm run deploy:sites -- publish purpur --apply
npm run deploy:sites -- plan stonehaus
npm run deploy:sites -- publish stonehaus --apply
```

[Purpur](../../apps/purpur/deployment.md) содержит PHP и занимает отдельные имена в общем document root. Receiver обновляет только эти имена, сохраняя Memo и Stonehaus. [Stonehaus](../../apps/stonehaus/deployment.md) публикует три варианта одной проверенной поставкой. Обе процедуры требуют успешного Harness для точного SHA, сверяют установленный receiver/назначение и проверяют реальные HTTPS-байты приложения и соседей. Ключ остаётся локальным. Поставка сайтов не запускается автоматически при push.

### 3.1. Универсальный статический помощник

Помощник предназначен для **статических сборок** с `index.html`. Стек приложения должен поддерживать такую поставку. PHP, базы данных, SSR и процессы backend требуют отдельной процедуры под реальное окружение и не публикуются этим помощником.

```bash
npm run timeweb -- check
npm run timeweb -- check example-app
npm run build --workspace=apps/example-app
npm run timeweb -- plan example-app
npm run timeweb -- publish example-app --apply
```

`check` без имени проверяет аккаунт из `connection.json`, с именем — конкретную цель. Он проверяет SSH, наличие rsync на сервере и доступность каталога. `plan` выполняет rsync в dry-run и показывает предстоящие изменения. `publish --apply` загружает содержимое сборки в выбранный каталог. Он запускается только в рамках порученной публикации после проверки приложения и просмотра плана.

Помощник не создаёт каталоги и не удаляет устаревшие файлы. Файлы с теми же именами будут заменены. Обновление выполняется на месте, без гарантии атомарности и автоматического rollback. Для восстановления до публикации сохраните предыдущую сборку вне публичной папки или убедитесь, что доступна нужная резервная копия хостинга. Публикация предыдущего артефакта восстанавливает его файлы, но не удаляет новые файлы, появившиеся позже.

Нельзя направлять несколько приложений в один document root или отправлять туда корень монорепозитория. Скрипт отказывает при обнаружении symlink, `.env`, служебных каталогов и файлов ключей в сборке. Проверьте, что в артефакте нет серверной конфигурации и приватных данных.

После передачи проверьте HTTPS-адрес, загрузку ресурсов, обновление вложенного маршрута и основной пользовательский сценарий. Успешный rsync подтверждает передачу файлов, а не работоспособность сайта.

## 4. Деплой из GitHub Actions

У Memo настроен конкретный [workflow](../../.github/workflows/deploy-memo.yml). После успешного Harness для текущего `main` выпуск запрашивается командой `npm run release:memo` или ручным запуском workflow на `main`. Обычный push в `main` выполняет только проверки.

Actions публикует проверенный артефакт в `deploy/mind-assistant`. Задание Timeweb забирает его по HTTPS, сверяет CI и сумму, сохраняет backup и выполняет поставку только в каталог Memo. Workflow ожидает подтверждение опубликованного релиза. SSH-ключи и пароли MySQL в GitHub не хранятся. Полная настройка, ограничения и восстановление — в [инструкции приложения](../../apps/memo/deployment.md).

Для другого приложения подготовьте собственные сборку, назначение и процедуру. Упоминание GitHub Environment в YAML само по себе не включает правила защиты. [Документация GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

## 5. Восстановление и PHP-приложения

Для PHP/MySQL применяется процедура выбранного приложения. У Memo это [поставка](../../apps/memo/deployment.md) и [изолированная проверка восстановления SQL-копии](../../apps/memo/recovery.md). Статический помощник не расширен до мигратора БД. На локальном macOS Docker обеспечивает PHP/MySQL, на хостинг передаётся готовый артефакт приложения.

Перед перезаписью известны предыдущий артефакт и резервная копия затронутых данных/загрузок/конфигурации вне публичного каталога. Откат файлов совместим не с любой версией схемы. Для необратимых изменений может потребоваться восстановление согласованной пары или исправление вперёд. Успешное создание backup не подтверждает восстановление. Проверять restore нужно в изолированной разрешённой среде с ограничением исходящих писем, webhooks и заданий.

Подробные процедуры для агента: [восстановление](../../.agents/skills/timeweb/references/recovery.md), [PHP/MySQL](../../.agents/skills/timeweb/references/php-mysql.md). Подготовленная инструкция не является проведённым деплоем или восстановлением production.
